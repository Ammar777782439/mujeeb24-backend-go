# دورة حياة فريق التاجر في Mujeeb 24

## الهدف والحدود

هذه الدورة تجعل **Mujeeb/PostgreSQL** مصدر الحقيقة الوحيد لأعضاء الفريق ودعواتهم وإسناد المحادثات. وهي لا تنشئ دفعًا أو شحنًا أو حسابات جديدة تلقائيًا، ولا تستعمل Chatwoot. لا يملك مزود القناة أو نموذج الذكاء الاصطناعي صلاحية إنشاء عضو أو تغيير دوره أو رؤية رمز دعوة.

| الكيان | مصدر الحقيقة | الغرض |
| --- | --- | --- |
| `principals` | PostgreSQL | هوية حساب المستخدم، بريده وحالته العامة. |
| `business_memberships` | PostgreSQL | علاقة المستخدم بالتاجر، دوره وحالة عضويته. |
| `team_invitations` | PostgreSQL | دعوة مقيدة بتاجر وبريد ودور ووقت انتهاء. تحفظ SHA-256 للرمز فقط. |
| `platform_super_admins` | PostgreSQL | صلاحية منصة منفصلة عن عضوية التاجر، لا تمنح وصولًا صامتًا للمحادثات. |

## الأدوار والصلاحيات

| الدور | إدارة أعضاء الفريق | استلام إسناد محادثة | تنفيذ إسناد محادثة |
| --- | --- | --- | --- |
| `owner` | نعم | نعم | نعم |
| `admin` | نعم | نعم | نعم |
| `manager` | لا | نعم | نعم |
| `agent` | لا | نعم | نعم |
| `analyst` | لا | لا | لا |
| `viewer` | لا | لا | لا |

لا تسمح واجهات إدارة الفريق العادية بإسناد دور `owner` أو نقل الملكية. نقل الملكية يحتاج قرار API مستقلًا، تدقيقًا، وخطوات أمان لا تدخل في هذه الدفعة.

## مسار الدعوة والقبول

> **قرار V1:** قبول الدعوة يتطلب مستخدمًا مسجّلًا ومصادقًا بالفعل. لا ينشئ قبول الدعوة `principal` جديدًا ولا يرسل بريدًا تلقائيًا.

1. ينشئ `owner` أو `admin` دعوة لبريد معيّن ودور غير `owner` ومدة لا تتجاوز 30 يومًا؛ الافتراضي 7 أيام.
2. يولّد التطبيق رمزًا عشوائيًا قويًا مرة واحدة. لا يكتب الرمز الخام في قاعدة البيانات أو الـlogs؛ يخزّن `SHA-256(token)` فقط.
3. يتلقى مدير التاجر الرمز في استجابة الإنشاء لمرة واحدة لكي يمرره عبر قناة خارجية يختارها. إرسال البريد أو الإشعار الخارجي ليس جزءًا من V1.
4. يرسل الموظف المصادق رمز القبول. تقارن قاعدة البيانات hash، وتتحقق ذريًا من أن الدعوة `pending` وغير منتهية، وأن بريد `principal` النشط يطابق بريد الدعوة.
5. في العملية الذرية نفسها تتحول الدعوة إلى `accepted` ويُنشأ أو يعاد تفعيل `business_membership` بالدور المتفق عليه.

الدعوة المنتهية أو المقبولة أو الملغاة لا يمكن قبولها. لا تعرض استجابات القراءة hash الرمز ولا الرمز الأصلي.

## تغيير الدور والإلغاء

يمكن لـ`owner` أو `admin` تغيير دور عضو نشط إلى دور غير `owner`، أو إلغاء عضويته. لا تقبل هذه المسارات معرّفات نصية حرة؛ تستخدم `principal_id` بصيغة UUID ضمن `business_id` محلول من JWT. قاعدة PostgreSQL تقفل صفوف الملاك النشطين عند الإلغاء وتمنع تحول التاجر إلى صفر ملاك نشطين.

إلغاء العضوية لا يحذف `principal` ولا يمس عضوياته في تجار آخرين. لن يتمكن عضو ملغى أو معطّل من استلام إسناد جديد، لأن الإسناد يحل عضوية نشطة داخل التاجر نفسه أثناء معاملة تحديث المحادثة.

## الإسناد اليدوي والأتمتة

يستقبل الإسناد اليدوي `assignee_principal_id` فقط. يرفض النظام أي UUID غير صالح، أو عضو غير نشط، أو عضو خارج التاجر، أو دور `analyst/viewer`. يخزّن UUID في حقل المرجع الحالي للمحادثة حفاظًا على توافق المخطط القائم، لا اسمًا حرًا.

تستخدم أتمتة `assign_human` payload المقيد التالي فقط:

```json
{"assignee_principal_id":"00000000-0000-0000-0000-000000000000"}
```

عند فشل الأتمتة بسبب عضو غير صالح، تسجل execution بنتيجة `failed` وسبب معروف، لكن لا تفشل materialization لحدث القناة ولا ترسل رسالة تلقائية. هذه القاعدة تمنع فقدان رسالة العميل بسبب قاعدة أتمتة سيئة.

## مالك المنصة

`platform_super_admin` هو أساس bootstrap وتدقيق داخلي فقط في هذه المرحلة. لا يتحول تلقائيًا إلى `business_membership`، ولا يستطيع قراءة محادثات التجار أو الرد باسمهم أو الوصول العابر للتجار من خلال ScopeProvider. أي عملية منصة مستقبلية يجب أن تعرّف نطاقها، سببها، أثرها التدقيقي، وآلية الموافقة قبل فتح API لها.

## نطاق API التالي

واجهات HTTP التالية ستصل طبقة التطبيق الموجودة في الدفعة التالية: قائمة الأعضاء، إنشاء دعوة، قبول دعوة، تغيير دور، وإلغاء عضوية. يجب أن تولد OpenAPI من DTOs Huma وأن تحتوي Postman على أمثلة غير حساسة. قبل commit أو push يلزم تشغيل unit وvet وOpenAPI drift وPostman JSON وفحص diff، أما PostgreSQL integration فلا توصف بأنها ناجحة من دون `POSTGRES_TEST_DSN` عامل.
